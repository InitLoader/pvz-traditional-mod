# 大规模扩展架构审计（植物 / 僵尸 / 子弹 / UI / 事件）

> 状态：基于当前 `0.10.x` 源码的设计审计，记录日期 `2026-07-23`。本文不表示 Lua、外部 DLL 插件、真正的新僵尸类型或通用 UI 系统已经实现。
>
> 配套目标方案见 [`SCRIPTABLE_SKILLS_AND_BEHAVIORS.md`](SCRIPTABLE_SKILLS_AND_BEHAVIORS.md)。本文回答的是：现有基础在扩展包、定义和场上实例大幅增加后会在哪里出问题，以及在开放 Lua/DLL 生态前必须补齐什么。

## 1. 结论

当前架构适合“少量、经过验证、彼此知道对方的内置垂直切片”，不适合直接承载大量互不协调、独立发布的植物、僵尸、子弹、UI 和插件。

这不是说现有代码应推倒重写。当前按模块隔离 Hook、验证 1051 版入口字节、配置失败回退原版、外部资源限路径、运行时状态侧挂等做法都值得保留。真正需要替换的是这些模块之上的**扩展控制面**和这些模块之下的**高频派发方式**。

如果现在只把上限调大并允许任意注册，问题大致按以下顺序出现：

1. **语义和 ID 先冲突**：多个包共用全局字符串 ID、数字 ID 和单文件配置，无法判断谁拥有定义、谁覆盖谁。
2. **原版类型天花板暴露**：当前自定义植物仍复用 `templatePlantId`，精英僵尸仍依附原版僵尸，自定义子弹仍映射原版投射物；增加注册项不等于增加真正的原生类型。
3. **热路径出现乘法成本**：活跃实体数 × 每 Tick/Draw 事件数 × 匹配处理器数，远比“注册了多少定义”更危险。
4. **生命周期错误积累**：裸指针侧挂、缺少统一删除事件和世代校验会产生陈旧状态、误命中复用地址或无法安全热重载。
5. **32 位内存先于条目上限耗尽**：动画、贴图和脚本状态只有单项数量限制，没有全局解码后字节预算。
6. **UI 和 Hook 发生所有权冲突**：多个扩展若各自 Hook `Update/Draw/MouseDown` 或直接修改图形状态，顺序、输入焦点、裁剪和崩溃隔离都无法管理。

因此，不能把“支持很多扩展”定义为把数组上限从 256 改到 4096。正确目标是：

- 注册量增长主要影响加载时间和注册表内存；
- 运行时成本只与**活跃实例及已预筛选的匹配处理器**相关；
- 资源按实际解码字节受预算约束；
- 所有内容、订阅、能力和 UI 节点都能追溯到 `ownerId + generation`；
- 一个包失败、禁用或重载时，不留下半注册状态，也不影响无关包。

## 2. 当前基础架构

### 2.1 启动和 Hook

当前启动链路为：

```text
DllMain
  └─ InitializeModThread
       └─ InstallPvZHooks
            ├─ 外部贴图 / 外部动画初始化
            ├─ 精英僵尸 Hook
            ├─ 波次 / 阳光 / 植物攻击 / 僵尸属性 Hook
            └─ 选卡 UI / 自定义植物 / 文本 Hook
```

`pvz_hook.cpp` 直接知道所有固定模块，并按顺序调用 `Install...Hooks`。源码中约有 30 处 `CreateAndEnableHook` 调用，以及大量写死的 1051 版 RVA、对象字段偏移和裸汇编桥。这种结构的优点是入口明确、便于逐点逆向验证；缺点是每增加一个可扩展语义都容易继续增加核心 Hook 或模块间直接依赖。

`CreateAndEnableHook` 当前会创建后立刻启用。一个模块安装多个 Hook 时，如果中途失败，前面已经启用的 Hook 不会自动回滚。因此现状能做到“模块失败时记录日志”，但还不是严格的模块级安装事务。

### 2.2 配置和资源

当前配置按领域拆分，解析器与 Hook 多数已经分离：

- 植物、僵尸、波次、阳光、精英、选卡 UI 各自读取固定文件；
- 外部贴图和动画拥有独立只读注册表；
- 多数配置使用 `schemaVersion: 1`、字段范围和重复 ID 校验；
- 部分运行时在解析失败时保留上一份有效配置。

但目前“一个领域一个总文件”仍把所有作者放进同一命名空间和同一失败域。配置热重载也不一致：植物目录、精英、贴图和动画主要在启动时加载；僵尸、植物攻击、阳光等运行时会在调用 `Current()` 时检查文件修改时间。后者会把文件系统查询和互斥锁带进游戏回调，而且多个文件不会作为同一个包世代同时切换。

### 2.3 事件、技能和实例状态

当前 `zombie_event_bus` 只有僵尸初始化和啃食伤害修正两类接口。它在注册时去重，但没有所有者、优先级、阶段、取消令牌或卸载；每次派发都会在互斥锁内复制整个监听器数组，再逐个调用。

`elite_skill_registry` 是全局 `string -> function pointer` 映射。每个精英的每个技能在 Update、Draw、Attack 等事件中再次按字符串查表并加锁。它能支撑当前一个 `BERSERK` 示例，但不应直接扩成数百个 Lua/DLL 处理器。

当前实例扩展状态分散在多个全局 `unordered_map<void*, ...>` 中：

- 精英僵尸状态带原版 `instanceId` 校验，并在 Delete Hook 中移除，这是可复用的安全方向；
- 自定义植物和子弹状态按裸指针保存，初始化时覆盖旧项，但没有统一的植物/子弹 Remove 事件和实例世代；
- 僵尸防具、特殊头部、覆盖动画和选卡屏幕又分别维护各自的互斥锁和侧挂表。

随着功能增加，如果每个模块再建一张 `void*` 表，单个实体一次 Update 可能触发多次哈希、加锁和生命周期核对，也很难证明删除时已经清理所有模块。

## 3. 当前可见容量与真实含义

| 领域 | 当前可见边界 | 实际含义与隐藏限制 |
| --- | --- | --- |
| 自定义植物 | 配置最多 512 条，逻辑 ID `1000..30000` | 仍映射 `templatePlantId 0..48`；按逻辑 ID 查找是线性扫描；Chooser 类型由向量位置派生，包顺序改变会改变临时类型 |
| 植物攻击 / 子弹 | 自定义植物的 `projectileType` 为 `0..13`，当前表处理 11 类常见原版投射物 | 不是任意新子弹类；来源依靠开火期间的 `thread_local` 指针推断，延迟、嵌套和二次生成会变复杂 |
| 僵尸 | 出怪和精英候选仍使用原版 ID `0..32` | 精英是原版实例的侧挂变体，不是真正扩展原版枚举、构造分派和存档格式 |
| 精英 | 最多 128 个定义、每精英 16 个技能、64 个视觉替换 | 生成时逐条扫描定义和候选 ID；每个活跃精英在 Update/Draw 中逐技能字符串派发 |
| 外部贴图 | 最多 256 个 ID | 首次解析会同步走路径核对和原版图片加载；没有全局像素/解码字节预算和包级配额 |
| 外部动画 | 最多 256 个动画 | 单动画还允许 512 轨、每轨 20000 帧、总计 500000 Transform；数量上限无法阻止总内存爆炸 |
| 选卡 UI | 每页固定 40 张 | 每个选择器保存全部自定义卡；当前 Draw 会复制整份卡片向量，Update 和命中测试仍有全表扫描 |
| 僵尸事件 | 2 类基础事件 | 无所有者、阶段、优先级、Token、预算和统一异常边界；派发复制监听数组 |
| 精英技能 | 一个 ID 对应一个 C++ 回调 | 同名只能失败，不能表达事件多订阅者与 Capability 单 Provider 的不同语义，也不能按包卸载 |

这些数字只说明解析器会拒绝更大的单文件，不是安全容量证明。尤其是动画：理论上的 `256 × 500000` 个 Transform 远超一个 32 位游戏进程可接受的地址空间，而运行时还会同时保留 Raw 数据、字符串、C++ 容器和 44 字节的游戏 ABI Transform。

## 4. 大量扩展时会发生什么

### 4.1 包、ID 和覆盖冲突

当前资源 ID 只允许字母、数字和下划线，没有包命名空间。两个作者都注册 `FIREBALL`、`BERSERK` 或 `BOSS_IDLE` 时只能冲突；如果未来采用“后加载覆盖”，结果又会依赖目录枚举和加载顺序，无法复现。

数字 ID 的问题更严重：

- 原版 ID、Mod 稳定内容 ID、当前进程临时句柄和存档 ID 现在还没有完全分层；
- 自定义植物的 Chooser 类型依赖向量位置，增加、删除或重排包会改变映射；
- DLL、Lua 和 JSON 若分别维护 ID 规则，跨层引用无法统一检查。

目标规则必须是：发布内容使用 `namespace:name` 形式的稳定 `ContentId`；进入注册表后转为带世代的紧凑 `ContentHandle`；只有靠近原版桥接时才临时映射为原版载体 ID 或槽位。原版数字 ID 不能承担跨包身份。

### 4.2 大量自定义植物

当前 `FindCustomPlantByLogicalId` 对可见植物做线性扫描，Cost、Refresh、Initialize 等入口都可能调用解析。512 条仍可能勉强可用，但数千条、多包合并和更多 Hook 叠加后不应继续依赖扫描。

更关键的是，当前植物只是“逻辑 ID + 原版模板状态机 + 可替换主体动画/数值/投射物”。如果作者注册 1000 个植物，它们并不会自动获得 1000 套独立目标选择、生产逻辑、升级关系、模仿者处理、图鉴和存档槽位。没有 Archetype/Behavior 分层时，注册量只会放大模板分支和特殊情况。

需要改为：

- `ContentId -> PlantDefinition` 和临时 Chooser Handle 都使用 O(1) 索引；
- `PlantDefinition` 明确 `carrierPlantId`、行为集合、资源集合、卡片元数据和兼容声明；
- 场上实例只保存 `PlantHandle + BehaviorSetId + InstanceGeneration`，不长期保存可能在热重载后失效的向量元素指针；
- 植物删除路径发布统一 Remove 事件并撤销全部侧挂状态。

### 4.3 大量自定义僵尸和精英

`PickEliteZombie` 当前会为每个生成实例扫描全部精英定义，再扫描每个定义的 `eligibleZombieIds`。128 条问题不大，若扩成数千定义则生成成本与全局注册量线性增长。

应在加载事务中预编译：

- `carrierZombieId -> 候选精英/Archetype` 索引；
- 按优先级和稳定 ID 排序的候选桶；
- 概率抽取需要时建立前缀权重或 Alias 表；
- 每个实体只绑定已经解析的 `BehaviorSetId`，Update/Draw 不再逐技能做字符串注册表查询。

真正新僵尸还需要解决原版创建分派、动画组合、特殊状态、出怪规则、碰撞、掉头/防具、死亡、音效和存档等路径。首阶段应明确采用“原版载体 + 自定义 Archetype/行为”的虚拟类型，而不是宣称简单增加 JSON 数字即可无限扩原版 `ZombieType`。

### 4.4 大量自定义子弹

当前子弹侧挂只记录来源植物逻辑 ID 和伤害，并通过“植物正在同步调用原版 Fire”这一线程局部上下文确定来源。这对当前同步多发垂直切片有效，但以下情况会失真：

- 计时器延迟生成；
- 子弹命中后再生成子弹；
- 反弹、分裂、转属、复制；
- 一个回调嵌套触发另一植物开火；
- 地址复用后旧侧挂尚未清理。

后续必须有 `ProjectileArchetype`、显式 `SpawnProjectileCommand` 和带世代的 `ProjectileHandle`。来源、阵营、伤害类型、命中策略、视觉、父实例和所有者都随命令传递，不能再从调用栈偶然推断。子弹命中与删除 Hook 在完成逆向验证后应由核心只安装一次，再发布语义事件。

### 4.5 大量贴图和动画

当前注册表按 ID 查找是合理的，但资源生命周期和预算还不适合大包：

- 贴图第一次使用时，在全局贴图互斥锁内做路径规范化、文件检查和原版同步解码；多个首次加载可能造成明显卡顿；
- 动画启动时解析全部元数据和 Raw/compiled 内容，首次注入时再构建一份游戏 ABI Definition；Raw 与运行时 Transform 会同时占用内存；
- 只有单文件/单动画上限，没有所有包合计的文件字节、解压字节、Transform、纹理像素和已构建 Definition 上限；
- 已交给原版的图片和 Definition 不能在仍被引用时随意卸载。

资源系统需要“两阶段加载”：启动时只登记 manifest 和轻量元数据，验证引用图；进入关卡或首次使用前在安全点预热实际资源。每个资源都记录预计/实际内存、引用状态、所有者和失败原因。预算必须同时有每包和全局值；超过预算时拒绝新世代，而不是加载一半后等待进程崩溃。

### 4.6 大量 UI 和自定义卡片

当前选卡扩展是一个专用实现，不是通用 UI 框架。它在 Draw 中复制全部卡片状态，再绘制当前页、银行和飞行动画；在 Update/命中测试中也会扫描卡片。500 张卡片的主要问题已经不只是 CPU，而是几十页翻找、分类、搜索、排序、冲突提示和输入焦点。

若多个 DLL 各自 Hook `Draw/Update/MouseDown`，还会出现：

- 绘制顺序依赖插件加载顺序；
- 一个插件未恢复 Clip/Colorize/Transform，污染后续原版或插件绘制；
- 两个面板同时消费鼠标/键盘；
- 一个面板关闭后仍留下输入捕获或裸指针；
- Lua 在 Draw 高频路径超时，使整个画面卡顿。

需要唯一 `UiHost`：核心拥有 Hook，扩展只注册声明式面板、数据源和受限绘制命令。`UiHost` 统一处理层级、布局、裁剪、焦点、捕获/冒泡、可见性和每帧预算；目录类 UI 使用虚拟列表，只为可见行创建节点。首版不应把原版 `Graphics*` 或任意 Draw 回调直接暴露给 Lua。

### 4.7 大量事件和 API 注册

事件订阅者很多并不一定慢；**让所有订阅者匹配所有实例的高频事件**才会慢。朴素成本近似为：

```text
每秒回调数 = 活跃实例数 × 每秒事件频率 × 每实例匹配处理器数
```

例如仅作压力示意：300 个活跃实例、60 次/秒 Update、每实例误匹配 100 个处理器，会产生 180 万次回调/秒，还未计算 Lua 指令、字符串查找、锁和命令生成。即使全局只注册 100 个处理器，也可能不可接受。

因此统一事件中心必须做到：

- 注册时把字符串事件/行为/过滤器编译为数字 ID 和索引；
- 按事件、实体种类、载体类型、行为集合和阶段预分桶；
- 同一 Lua 行为每个事件只注册一次，实体只绑定 BehaviorSet，不按实体重复注册全局回调；
- 派发使用不可变快照，不持注册锁，不做文件 I/O，不构造临时字符串，常见路径不分配堆内存；
- 同步可修改事件和延迟通知事件分开；递归、命令数和二次事件深度都有上限；
- 事件允许多个订阅者，Capability 默认只允许一个 Provider，可叠加修正使用显式 Modifier Pipeline。

### 4.8 配置热重载和多包合并

如果继续让每个 Hook 自己轮询一个文件，会出现：

- 高频战斗回调反复调用 `exists/last_write_time`；
- 植物定义已经更新，动画或贴图仍是旧世代；
- 一个共享 JSON 中某个作者写错字段，整个领域配置被拒绝；
- 无法知道删除文件应该撤销哪个作者的注册；
- 多个文件互相引用时看到半新半旧状态。

正确流程是：文件监视器只发“需要重载”信号；后台或工具进程解析候选包；核心构建完整下一世代，验证依赖、ID、Schema、资源、Capability、配额和冲突；最后只在 Board 安全点原子切换。失败保留整个上一世代，并给出精确到包、文件和 JSON Pointer 的诊断。

### 4.9 日志、错误和恶意/失控扩展

当前日志每条消息都会获取全局锁并重新打开文件追加。内置模块低频记录时足够可靠，但数百扩展在 Update 中刷日志会直接造成磁盘 I/O、巨型日志和帧抖动。

需要异步有界日志队列、按所有者/消息键限速、重复折叠和丢弃计数。诊断面板应显示每个所有者的注册数、活跃实例、回调次数、总耗时、最慢事件、命令数、Lua 内存、资源内存和最近错误。超过预算先节流或禁用对应所有者，不能把整个事件系统一起关闭。

原生 DLL 无法像 Lua 一样可靠隔离：它能访问进程全部内存，访问冲突后即使 SEH 捕获也可能已破坏状态。因此原生插件必须视为可信代码；预算、耗时和崩溃日志只能帮助定位，不能承诺真正沙箱。

### 4.10 存档、重放和确定性

当前自定义内容还没有统一存档层。内容包数量增加后必须处理：

- 存档引用稳定 `ContentId`，不能引用向量序号或本次进程的 Handle；
- 存档记录包 ID、版本、内容哈希和迁移版本；缺包时使用明确占位/拒绝策略；
- Lua 状态只保存 Schema 声明的数据，不能序列化闭包、裸句柄或 DLL 指针；
- 随机数必须来自宿主提供的确定性流。当前个别初始化仍使用 `GetTickCount`，不适合作为可重放技能随机源；
- 热重载切换世代后，旧实例要么继续绑定旧世代到安全销毁，要么执行显式状态迁移，不能静默套用结构不兼容的新定义。

## 5. 面向规模的目标结构

```text
扩展包 JSON / Lua / DLL manifest
              │
              ▼
PackageRegistry + DependencyResolver
              │ 构建候选世代
              ▼
ExtensionTransaction
├─ ContentCatalog       # Plant/Zombie/Projectile/UI/Resource 的稳定 ID 与索引
├─ EventRegistry        # 预编译订阅、阶段、过滤器、配额和不可变快照
├─ CapabilityRegistry   # 版本化单 Provider / 显式 Modifier Pipeline
├─ AssetRegistry        # 元数据、懒加载、引用、内存估算与预算
├─ UiHost               # 布局、虚拟化、输入路由和受限绘制命令
└─ Diagnostics          # owner 级计数、耗时、错误、内存和来源
              │ 全部验证成功
              ▼
Board 安全点原子提交 generation
              │
              ▼
EntityRuntime + CommandBuffer
├─ EntityHandle(type, slot, instanceGeneration)
├─ BehaviorSetId
├─ owner/state sidecar
└─ 延迟生成、删除、伤害、动画与 UI 命令
```

### 5.1 一个内容四种身份

每个自定义内容必须区分：

1. `ContentId`：稳定字符串，如 `author.pack:ice_pea`，用于配置、依赖和存档。
2. `ContentHandle`：本世代内的紧凑数字句柄，用于 O(1) 注册表访问。
3. `EntityHandle`：场上实例句柄，包含类型、槽位和实例世代，防止地址复用。
4. `CarrierId`：最终桥接原版时使用的植物/僵尸/子弹模板 ID，不对外作为内容身份。

只要这四者混在一起，大量扩展就会在重排、重载、存档或跨包引用时出错。

### 5.2 注册期编译，运行期只查索引

加载事务应预先完成：

- ID intern、依赖解析和引用链接；
- 植物/僵尸/子弹按 Carrier、标签和事件建立反向索引；
- Lua 函数解析为稳定函数引用；
- JSON MicroRule 编译为预过滤订阅和固定命令；
- DLL Capability 查找并锁定主版本；
- 每种 Archetype 生成不可变 `BehaviorSet`；
- UI 数据源建立搜索索引和虚拟列表模型；
- 资源计算解码后大小上界和包级预算。

运行期常见 Update/Draw/Hit 路径不再解析字符串、读取 JSON、查询文件时间或扫描全部注册内容。

### 5.3 容量不是一个数字

运行时必须分别配置和报告：

| 容量维度 | 主要成本 | 必须限制/统计的内容 |
| --- | --- | --- |
| 包和定义数 | 启动时间、索引内存、冲突检查 | 每包/全局定义、依赖边、Schema、字符串池 |
| 活跃实体数 | 侧挂状态、原版对象池、每 Tick 工作 | 按植物/僵尸/子弹类型计数和峰值 |
| 事件订阅数 | 快照内存、匹配计划 | 每事件、每所有者、全局订阅及撤销数 |
| 匹配回调数 | 直接帧时间 | 每事件/所有者调用次数、总耗时、P95/P99 |
| Lua 状态 | 32 位堆、GC 停顿 | 每 VM 内存、指令、临时分配、GC 时间 |
| 资源 | 地址空间和首次加载卡顿 | 文件、解压、像素、Transform、ABI Definition 实际字节 |
| UI | Draw/布局/输入成本 | 可见节点、DrawCommand、命中区域、文本测量和列表虚拟化命中率 |
| 命令/事件递归 | 队列爆炸和逻辑死循环 | 每帧命令、每实体命令、递归深度、二次事件数 |

对外不应宣传“无限扩展”。应发布经过压力测试的容量档案，并注明测试硬件、场景、活动实例和资源规模。注册一万个未激活定义与让一百个脚本处理每个子弹 Update 完全不是同一种负载。

## 6. 开放扩展生态前的强制规则

### P0：不完成就不要开放第三方 DLL/Lua 注册

- 一个 Hook 目标只归核心 `HookBroker` 所有；普通插件不得各自 Hook 同一原版函数。
- Hook 安装先统一验证、再批量创建/启用；模块失败能完整回滚或保持明确的隔离状态。
- 建立 `ownerId + generation`，所有配置、内容、订阅、Capability、UI 和资源都必须可按所有者完整撤销。
- 建立稳定 `ContentId`、临时 `ContentHandle` 和带实例世代的 `EntityHandle`。
- 建立包级事务和安全点提交；禁止各 Hook 在热路径自行轮询配置文件。
- Event 与 Capability 语义分离，定义稳定顺序、阶段、重入规则和命令缓冲。

### P1：规模化运行所需基础

- 把植物、僵尸、子弹和 UI 定义接入统一 `ContentCatalog`，为常用查询建立 O(1) 或预编译索引。
- 把分散的裸指针侧挂迁移到统一实例槽和生命周期事件，优先补植物/子弹 Remove。
- 建立资源实际字节预算、懒加载/预热、引用追踪和 32 位地址空间余量告警。
- 建立 owner 级性能、内存、错误和日志限速；默认关闭 Lua 高频 Draw 回调。
- 建立 `UiHost`、虚拟列表和统一输入路由，选卡页只是其第一个适配器。

### P2：内容生态完整性

- 稳定存档、包锁定文件、缺包策略和 Schema 迁移。
- 包签名/哈希展示、原生权限告警、崩溃归因和兼容性报告。
- 跨包可选依赖、软引用、显式 Patch/Modifier 规则和冲突可视化。
- 根据真实基准决定是否增加更高容量档，而不是先提高解析器上限。

## 7. 压力测试与验收矩阵

以下不是对当前运行时的承诺，而是实现新架构时必须加入的测试类别。

| 场景 | 测试目的 | 通过条件 |
| --- | --- | --- |
| 100 个包、10000 个混合内容定义 | 包图、ID、索引和诊断规模 | 稳定结果；冲突精确归因；禁用一个包只撤销其所有内容 |
| 同一事件 100/1000 个混合订阅者 | 排序、快照和撤销 | 顺序确定；派发不持注册锁；无每次全量复制；重复注册可诊断 |
| 数百活跃植物/僵尸/子弹 | 实例句柄与热路径 | 地址复用不误命中；删除后侧挂归零；开销与匹配处理器而非全局定义数相关 |
| 事件产生事件、命令产生实体 | 重入和风暴 | 深度、每帧命令和每所有者配额生效；单包被节流时其他包继续运行 |
| 多个接近单项上限的动画/贴图 | 32 位资源预算 | 候选世代在提交前按实际/估算字节拒绝；不出现半加载注册表 |
| 两包声明同 ID、Provider、UI 插槽或修改同字段 | 冲突治理 | 不使用“最后加载者获胜”；显示所有者、来源和可选解决方案 |
| 同时修改植物、脚本、动画和贴图 | 热重载原子性 | 全部成功后一次切换；任一失败保留完整旧世代 |
| 5000 个目录条目和多面板 | UI 虚拟化与输入 | Draw/命中成本与可见节点相关；焦点、层级和关闭清理正确 |
| 保存后删除/升级包 | 存档兼容 | 缺包和迁移结果确定且可解释；绝不把旧 Handle 当成新内容 |
| DLL 慢回调/异常，Lua 死循环/超内存 | 故障边界 | Lua 只禁用对应模块；DLL 明确报告可信原生风险；其他所有者诊断仍可读取 |

性能验收不应只写固定毫秒数。先在最低支持硬件建立“无扩展基线”，再要求扩展层 Update/Draw 的 P95/P99 开销保持在约定的基线比例内。无论最终比例是多少，以下不变量应直接进入自动测试：

- 高频派发不做文件 I/O、JSON 解析和日志文件打开；
- 常见派发不产生堆分配，不构造字符串，不复制全订阅数组；
- 注册/撤销期间才构建新不可变快照，回调期间不持注册锁；
- 相同包集合、版本、种子和输入序列产生相同注册顺序与逻辑结果；
- 每个所有者的资源、回调、命令和错误都能单独统计并一键禁用。

## 8. 对现有路线的调整建议

现有三级扩展方向正确，但实现顺序必须把规模化地基放在 Lua 和 DLL 之前：

1. 先增加只读诊断和基准，记录现有 Hook、每帧实体量、事件次数、资源内存和选卡 Draw 成本。
2. 实现 `PackageRegistry / owner / generation / ExtensionTransaction`，先承接现有固定 JSON。
3. 实现 `ContentCatalog / EventRegistry / CapabilityRegistry / CommandBuffer`，用适配器接入 `zombie_event_bus` 和 `elite_skill_registry`。
4. 迁移植物、僵尸、子弹侧挂为带世代句柄，补齐删除事件和预编译 BehaviorSet。
5. 实现资源预算、预热和统一 `UiHost`，再开放大量内容注册。
6. 接入 Lua，并用 `BERSERK`、三连发、分裂子弹和一个虚拟列表面板做纵向验证。
7. 最后冻结并发布 DLL C ABI；否则过早发布的 ABI 会把裸指针、字符串热查找和缺少所有者的缺陷永久固化。

现有 Hook 不需要一次性重写。它们应逐个变成“版本专用桥”：读取必要寄存器/字段、构造语义事件、调用统一运行时、应用经过验证的命令，然后返回原版。插件和 Lua 只看语义层，不知道 RVA、调用约定和对象偏移。

## 9. 最终判断

当前项目可以继续增加少量内置植物变体、精英、资源和 UI 功能，但**不能只靠提高 JSON 上限或开放更多注册函数来安全支撑大型生态**。

要支持大量扩展，核心不是更多专用 API，而是以下六个基础能力：

1. 稳定且有所有者的内容身份；
2. 事务化包加载和依赖/冲突治理；
3. 带实例世代的统一生命周期；
4. 预编译、可预算、无热路径锁的事件派发；
5. 受全局与每包字节预算约束的资源系统；
6. 核心独占 Hook、统一 UI 与命令缓冲。

完成这些以后，注册数可以很大而不直接拖慢每帧；真正决定性能的将是场上活跃实例、匹配回调、脚本工作量、UI 可见节点和实际解码资源。这个边界可测试、可诊断，也比宣传“无限自定义”更可靠。

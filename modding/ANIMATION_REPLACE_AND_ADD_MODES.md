# 动画接入模式：替换原版与新增实体

## 为什么必须拆成两个模式

“把原版普通僵尸的动作换掉”和“增加一个拥有独立 ID、属性、AI、状态机的新僵尸”不是同一件事。

- **替换原版动画**：目标是已有植物或僵尸 ID，只给该目标绑定新的主体 `animationId`。原实体的生命、攻击、防具、AI、出怪和存档身份应保持不变。
- **新增实体**：创建新的逻辑 ID、属性、状态机、资源所有权和存档身份。模板最多只能作为兼容载体，不能把新实体伪装成某个原版 ID 的配置覆盖。

旧制作器把两者合并在一条“新增僵尸”路径中，导致普通动画替换也生成新增僵尸描述，并把生命和攻击一起写入 `zombies/attributes.jsonc`。这既容易误改玩法，也让使用者误以为真正的新 ZombieType 已经存在。

工程 schema 5 起增加 `integrationMode`：

```json
{
  "schemaVersion": 5,
  "kind": "Zombie",
  "integrationMode": "ReplaceOriginal",
  "templateEntityId": 0
}
```

界面使用中文名称“替换原版动画”和“新增实体”。`templateEntityId` 在替换模式中表示目标原版 ID，在新增模式中表示兼容载体模板。

## 当前支持矩阵

| 实体 | 替换原版动画 | 新增实体 |
|---|---|---|
| 僵尸 | **可打包、可一键安装**。只合并 `zombies.<id>.animationId` | **只可导出 ZIP 骨架**。真正新增僵尸运行时未完成，拒绝一键安装 |
| 植物 | **可打包、可一键安装**。只合并 `plants.<id>.animationId` | **可打包、可一键安装**。当前仍是 `templatePlantId` 兼容路径 |
| UI/其他 | 可编辑和导出 Raw/compiled | 当前不生成实体安装包 |

制作器不能因为文件和 JSON 能生成，就宣称对应运行时已实现。ZIP 中的 `entity.fragment.jsonc` 必须写出 `mode`；新增僵尸还要写 `runtimeStatus: "planned"`。

## 替换原版僵尸的配置契约

替换普通僵尸 ID `0` 时只生成以下稀疏补丁：

```jsonc
{
  "schemaVersion": 1,
  "mode": "replaceOriginal",
  "targetKind": "zombie",
  "targetOriginalId": 0,
  "zombies": {
    "0": {
      "animationId": "MY_NORMAL_ZOMBIE_ANIMATION"
    }
  }
}
```

一键安装使用字段级合并。假设用户已有：

```jsonc
"0": {
  "bodyHealth": 540,
  "attackDamage": 120,
  "armorRolls": [ /* ... */ ]
}
```

安装后这些字段全部保留，只追加或更新 `animationId`。替换模式不得生成 `custom_zombies.generated.jsonc`，也不得从制作器的生命、伤害输入框覆盖原属性。

## 替换原版植物的配置契约

替换大嘴花 ID `6` 时只生成以下稀疏补丁：

```jsonc
// pvzmod/config/plants/attributes.jsonc
{
  "schemaVersion": 1,
  "plants": {
    "6": {
      "animationId": "MY_CHOMPER"
    }
  }
}
```

该补丁只改变目标原版植物的主体 Reanimation。阳光、冷却、生命、攻击状态机、子弹、卡片、原版 ID 和存档身份继续由游戏管理；未列出的植物不进入替换分支。外部动画必须保留目标植物状态机会请求的同名 `anim_*` 轨道，运行时会优先恢复替换前正在播放的同名动作，无法匹配时才回退 `initialAction`。

## 原版图片复用与资源所有权

动画轨道中的图片符号分成两类：

1. **原版引用**：图片来自游戏的 `reanim/`、`images/` 或原版资源表。发布时只保留 Reanimation 内的符号，省略 `animations[].images` 映射。运行时找不到外部映射时会继续使用原版 Definition 的图片。
2. **Mod 图片**：用户导入或替换的 PNG/JPG。只有被当前动画帧实际引用的图片才复制到 `pvzmod/images`，同时写入 `textures.jsonc` 和 `animations[].images`。

因此，替换一个僵尸的手臂图片时，只发布新的手臂；没有改动的身体、头、眼睛和防具继续复用游戏资源。不能为了编辑器预览方便而把整套原版图片重复安装。

`.pvza` 是便携工程，可以把原版预览图片嵌入文件，方便离线打开；但工程同时保存 `originalImageReferences` 来源标记。便携预览资产不会因此变成 Mod 自有资产，打包时仍会被排除。

这项规则同时减少：

- 启动时外部贴图注册和解码数量；
- 进程内重复纹理缓存与显存占用；
- Mod 包体积和不同 Mod 重复携带相同原版素材；
- 原版素材被错误当成作者自有素材再分发的风险。

## 编辑器工作流

### 替换原版动画

1. 直接打开游戏目录 `compiled/reanim` 下的原版动画；制作器自动选择“替换原版动画”。检测到 `Zombie_*`、`anim_bucket`、`anim_cone` 等主体轨道时自动选择僵尸。
2. 在工程检查器或发布确认窗口选择目标实体类型和原版 ID。
3. 修改轨道、动作或只替换需要变化的图片。未修改的原版图片保持“原版引用”。
4. 导出检查。植物和僵尸替换均可打包或一键安装，安装器只合并目标 ID 的 `animationId`。

这条路线不要求先“新建僵尸模板”，也不创建新增实体的数值字段。

### 新增实体

1. 新建植物或僵尸工程并选择“新增实体”。
2. 设置新逻辑 ID、显示信息、兼容载体和实体数值。
3. 制作动画和 Mod 自有图片。
4. 新增植物可使用当前模板兼容安装；新增僵尸只能生成未来运行时所需的资产骨架，直到独立 ZombieType/状态机/生命周期接入完成。

## 安装和校验顺序

一键安装必须按以下顺序执行：

1. 校验实体类型与接入模式是否属于当前支持矩阵。
2. 收集动画实际使用的图片符号，排除原版引用和未使用的调色板素材。
3. 校验资源 ID、路径和跨植物/僵尸载体冲突。
4. 建立事务备份。
5. 写动画、Mod 图片、贴图与动画注册。
6. 按模式写实体配置：新增植物写 `custom_plants.jsonc`；替换植物写 `plants/attributes.jsonc`；替换僵尸写 `zombies/attributes.jsonc`，两种替换都只稀疏合并 `animationId`。
7. 完整重读配置；任何一步失败时恢复所有文件。

## 旧工程与旧安装迁移

- schema 4 及更早的工程缺少模式字段，加载后仍以原有“新增实体”兼容默认值打开；发布前必须在最终检查窗口明确选择模式。
- 从可识别的原版资源目录加载旧工程时，制作器会把实际使用且可由原版索引解析的图片补记为原版引用。
- 旧版本可能已经生成 `pvzmod/config/zombies/custom_zombies.generated.jsonc`，或把原版图片复制进 `pvzmod/images`/`textures.jsonc`。升级不会自动删除这些文件，因为它们可能已被用户手工修改或被其他 Mod 引用。
- 清理旧文件前，应先用 Mod 管理器的所有者/引用关系确认无人使用，再删除孤立图片、纹理项和旧生成文件。当前制作器只保证后续发布不再制造这些冗余。

## 后续运行时工作

“新增实体”最终不能停留在模板套壳。真正新增植物/僵尸需要独立内容 ID、带 generation 的句柄、生命周期清理、动作控制器、可靠的动画帧事件、命令缓冲、投射物运行时和状态机。上述基础稳定后，再向 Lua 和 DLL 公布语义 API；动画制作器只负责资产及必要基础描述，安装、所有者、依赖和孤立资源清理由 `PvZModManager` 接管。
